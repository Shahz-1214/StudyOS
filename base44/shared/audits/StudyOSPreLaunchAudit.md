## 2. Prioritized findings and launch blockers

### P0/P1 — release blockers

**SEC-01 — FAIL: student uploads are public, not protected by entity ownership.**
Evidence: StudyLens and LectureMind call `Core.UploadPublicFile`; image preview uses that public URL; Lecture saves `audio_url`. Entity RLS protects records, not publicly readable media objects. Uploads can contain student names, faces, handwriting, school identifiers and other people's voices. No upload purpose/privacy notice or recording-rights confirmation accompanies the inputs.
Required remediation: use the native private-upload flow, keep file URIs rather than public URLs, authorize signed-file access server-side, validate file ownership/type/size and narrow follow-on AI operations. Preserve current text and lecture behavior. Existing public uploads require a separately approved inventory/cleanup plan; a new private uploader cannot retroactively revoke an old public URL. No destructive cleanup or migration performed. The current account had no saved Lecture rows, which does not establish that no orphaned or other-account uploads exist.

**SEC-02 — FAIL: the AI operations do not enforce entitlements.**
Evidence: all nine generation/analysis entry points authenticate a user and then call Core; none invokes an entitlement/usage guard. `checkEntitlement` is used by the Subscription page, not before those AI calls. Hints, Q&A, plan generation, failed requests and retries are not reliably accounted for. Several pages record a completion-named event before the AI request succeeds. Source-level defect confirmed; no exploit or charge-generating test was run.
Required remediation: one shared, server-side authorization/usage reservation/accounting mechanism reused by existing functions, with bounded inputs and concurrency/idempotency rules. Confirm commercial model and permitted deployment before changing protected billing/security architecture. A frontend button guard is insufficient.

**SEC-03 — FAIL: client-authoritative subscriptions and activity accounting.**
Evidence: useEntitlement.setPlan directly creates/updates SubscriptionState; its owner RLS permits those operations. `checkEntitlement` treats pro/elite as entitled without checking active status/expiry and seeds free subscriptions on reads. Counting only the latest 100 client-writable Events cannot secure a daily quota. Tightening subscription writes alone would break free-state creation; hiding UI alone would leave the API issue. Required: a coordinated, tested server-authoritative change, not a cosmetic fix.

**PRIV-01 — FAIL: non-essential analytics starts without a choice.**
Evidence: one SDK client initialized without `analytics.enabled: false`; installed SDK defaults to true, initializes tracking, schedules heartbeats and writes `base44_analytics_session_id` to localStorage. It includes pathname, referrer, event timestamp, session ID and authenticated user ID where available. `track()` forwards all provided event properties to analytics and separately creates an Event record. Onboarding includes educational/profile details; recommendation tracking includes free-text concept name; quizzes include scores and identifiers.
Separate evidence: Vite plugin `analyticsTracker: true` emits a page-view POST script in built index.html for top-level browsing. It hooks history changes and is not the same as SDK custom events. Iframe preview suppresses this script; preview observations alone would miss it.
Required: classify purposes, separate necessary app activity/usage accounting from product analytics, remove unnecessary educational data from analytics and decide disabling versus valid consent/opt-out handling for retained tracking. Any retained consent solution must gate collection before initialization, cover applicable platform page tracking/recordings, support reject/manage/withdrawal, and store only minimal versioned consent proof. Do not add a banner while automatic tracking remains outside its control. Do not remove Event records used by StudySync/entitlement without adjusting those consumers. Platform analytics/recording settings must be inspected by the operator; none was silently changed.

**LEGAL-01 — FAIL: no public policy or verified operator/contact details.**
No canonical privacy/terms/cookie pages or signup/footer policy links. No verified legal operator, deliberately public business address, privacy-request channel, complaint route, governing-law decision or support procedure available in code. Do not substitute Base44's corporate details for StudyOS's operator. Create policy/contact UI only around confirmed data; keep missing configuration internal. No fake contact or unsupported request workflow was added.

**LEGAL-02 — NEEDS VERIFICATION: minors and intended jurisdictions.**
The builder has explicitly confirmed worldwide targeting and an audience roughly age seven and up, so under-13 children and teenagers are intended users, not merely foreseeable visitors. Signup has no age decision, parental workflow or differentiated privacy treatment. No arbitrary minimum age was imposed. Confirm the precise eligibility/account-handling design and platform/provider suitability, then obtain qualified review of relevant age, consent, notice, safety and record-retention obligations before accepting children. See the confirmed-intent section and legal research below.

**PRIV-02 — FAIL: full retention/deletion promises cannot currently be delivered.**
Only isolated task/subject/concept/bookmark deletion exists. No full account-data export/deletion request flow, upload erasure, cascade cleanup, scheduled purge or disclosed backup-retention process was found. No evidence that deleting an account deletes every associated record/file/log/provider copy. Do not claim deletion on request until a real operator channel and tested procedure exist. Retention durations must be approved by the operator, not invented.

**DATA-01 — FAIL: academic context and verification claims exceed actual coverage.**
Onboarding stores country/board ID plus generic education level, not the full Country → Education System → Board → Qualification → Level/Class → Syllabus/Year → Subject hierarchy. SSC/HSSC remain qualification-level groupings; sub-board choice is deferred to external sites. Preset/custom subjects lack an explicit official-versus-custom identity. All inspected resources are board-wide links without subject/year coverage. Registry transformation hardcodes verified state/date; optional URL checks only detect availability failure and do not verify academic content. VerifiedNotes does not filter verification_status; resource cards print Verified unconditionally; PastPaperCard infers official status from resource_type without jointly checking authority. Do not reclassify or rewrite existing records without source evidence. Replace unsupported display assertions with accurate source/status wording, and validate academic context separately.

**PRODUCT-01 — FAIL: unsupported paid-plan and integration claims.**
Subscription shows prices, Unlimited AI, priority AI models, Galaxy layouts and RevenueCat purchase claims while the implemented controls only change a local subscription entity. No RevenueCat SDK/webhook, verified checkout or payment processing appears in active code. Installed Stripe packages are not evidence of integration. Prices/business promises were not verified. Remove unsupported purchase claims/actions only as part of the agreed entitlement remediation; do not invent refunds, billing terms or a provider.

### P1/P2 — safety, accuracy and user-flow defects

**AI-01 — FAIL: incomplete validation and cost bounds.**
Some text limits exist (essay 12,000, notes 8,000, problem 4,000) and quiz request counts are clamped. Other arrays/text/URLs are unbounded or not type-checked; previous hints, concept lists and lecture question need bounds. image/audio URL inputs are not tied to an authorized upload. Treat remote-resource abuse as a risk requiring validation, not as a proven SSRF exploit. Core calls are server-side (preserve this).

**AI-02 — FAIL: question validation can fabricate missing content.**
`sanitizeQuestions` fills missing options with Option N, substitutes Question N and defaults invalid answer indexes to zero. It does not prove factual correctness or consistently reject malformed output/oversized arrays. Custom-concept Practice can generate a trivial explicitly marked demo/placeholder question, which still flows into mastery scoring. Do not describe questions as academically validated or allow fabricated fallback questions to establish mastery. Improve the existing shared sanitizer rather than introducing a second validator.

**FLOW-01 — FAIL: quiz save failures still show completion.**
Practice, NoteQuiz and ExamPilot catch persistence errors, set answers and render Results with empty updates. completeQuiz saves an attempt before updating concepts, without an atomic/idempotent unit. Retrying after a partial failure can duplicate attempts. Required: truthful failed-save state, safe retry and test of partial writes; successful frontend rendering is not backend completion.

**FLOW-02 — FAIL: subject ambiguity can affect mastery mapping.**
NoteQuiz and adaptive exams map AI concept names across all subjects using a lowercased name dictionary. Duplicate concept names in different subjects can overwrite mappings. Notes selected for one subject may map to another. No cross-user access is implied; it is a within-user academic-integrity defect. Preserve subject/board identity in mapping and test same-name concepts explicitly.

**FLOW-03 — FAIL: incomplete duplicate/error handling.**
Tasks add lacks a submitting guard and catches neither load nor write errors. SavedPaper bookmark toggles are not guarded against rapid duplicates. Lecture Q&A's Enter handler can re-invoke while askBusy is true. OTP resend has no pending lock. Several handlers rely only on disabled buttons, not in-flight guards. Profile and vault operations hide errors or use browser alerts. Existing valid input is usually retained; preserve that behavior. Backend idempotency remains necessary where writes may repeat.

**FLOW-04 — FAIL: Vault note can be cleared by blur without editing.**
The input renders `noteDraft[id] ?? p.note`, but saveNote writes `noteDraft[id] ?? ''`. Focusing and leaving an existing note without typing can persist an empty value. Fix the existing handler to skip unchanged drafts or preserve the stored value; do not migrate notes automatically.

**FLOW-05 — FAIL: onboarding completion/empty-state mismatch.**
The profile is marked completed before all subject/concept writes finish. A partial failure can leave an onboarded profile with incomplete data. Empty registry messaging says users may continue without a board, while canNext requires country/board. Country labels mix actual countries with International/system categories. Required: truthful states, retry-safe writes, and hierarchy decisions; no invented boards/subjects.

**FLOW-06 — FAIL: search is not full personal-note or concept navigation.**
Home GlobalSearch searches already-loaded concept names and at most 200 board-resource titles. It does not search saved annotations, lecture transcripts or arbitrary personal notes; no standalone Note entity exists. Concept results route to generic Practice without selecting the concept. Concept navigation uses onMouseDown (keyboard activation does not perform it), note onMouseDown closes the panel before normal click completion, and blur closes it after a timer. No loading/error announcement. Board changes can retain stale results and the query does not filter active/verification state. Correct current component behavior; do not silently add a new notes product.

**EVENT-01 — FAIL: duplicate and misleading activity records.**
StudySync backend creates studysync_run, then the page calls track for the same event, creating another Event. App-open noise remains collected even when hidden from Recent activity. Multiple completion-named AI events fire before success. Event stores are mutable, despite comments calling them immutable. Baseline current-account data confirms app-open records. No events were deleted. Correct the single producer/consumer chain in the implementation phase.

**COPY-01 — FAIL: unsupported descriptions remain.**
Specific examples: Dashboard says notes are private despite public uploads; ErrorBoundary says data is safe without knowing save state; Progress says no estimates despite heuristic confidence-weighted mastery; features promises True/False and short-answer while QuizRunner is multiple choice; HelpCenter says before/after confidence although FocusStudy checks only after; Profile says Galaxy mode optimizes layout but no consumer was found; notification descriptions imply delivery while only local preferences exist; onboarding says education level tunes explanations but it is not sent to explainers. Streak display reads a stored field but no activity-driven streak update was found. Do not substitute different unsupported promises. No testimonial/review, award, partner-logo or fabricated user-count section was found in active application code.

**SEC-04 — FAIL / NEEDS VERIFICATION: errors and logs.**
Backend catches return `error.message` to callers. Login/register/reset and some study inputs render provider/raw error messages; AuthContext/ErrorBoundary and quiz pages log entire exception objects. Such objects can include internal request/response context. No secret value was found in inspected frontend code, and this is not evidence of an actual leaked credential. Map failures to safe user-facing messages and minimal operational logging; do not suppress actionable user errors. Browser network responses must also avoid internal details.

## 3. Security controls to preserve

- Private entities explicitly use creator-ID RLS for read/create/update/delete. Shared Boards/Resources/ExamSeries are public-read and admin-write. Keep these intended boundaries.
- Built-in User role is restricted to admin/user in the custom extension; User management remains platform-controlled. No custom auth backend exists.
- Every backend handler authenticates with auth.me(); registry import also checks admin before service-role database work. Other privileged Core calls are restricted to backend functions.
- safeReturnTo centralizes same-origin redirect filtering and strips bootstrap/token-style parameters; do not fork or weaken it.
- Existing output text is rendered through React rather than directly injecting AI HTML. The UI chart primitive's style injection is not proof of user-content XSS; inspect actual callers before any change.
- External resource anchors generally include noopener/noreferrer. In-app permissions are not to be replaced by frontend visibility checks.
- SDK token handling uses localStorage; that has XSS exposure characteristics, but replacing Base44 authentication/session architecture is not authorized by this audit. Review CSP/security headers and platform guidance. HTTP header configuration was not inspected live.
- Current-account read-only inspection cannot establish cross-user isolation. Two non-admin accounts and an admin must be exercised separately with intentionally isolated data.

Existing breakpoints, min-width guards, wrapping grids and fixed mobile navigation provide a foundation. However 367px/320px layouts need runtime checks: long subject/concept names next to unshrinkable status badges, resource authority labels next to bookmarks, unwrapped title/action rows, six-column onboarding labels and quiz metadata.
